## 1. 项目定位与成功标准

### 1.1 原始课程底线

项目必须使用 Python Turtle，并至少满足：

- 绘制不少于 3 种不同美食元素；
- 包含清晰文字标注；
- 使用颜色填充；
- 程序可正常运行，无语法错误；
- 具备动态效果和键盘/鼠标交互等进阶表现。

本项目的目标远高于底线：覆盖北京、天津、扬州、苏州、杭州五城，每城两道美食，以完整的交互叙事串联为一件作品。

### 1.2 核心体验定义

作品概念：**《运河四季·食味行舟》**。

用户不是点击普通菜单翻页，而是乘一艘小船沿运河探索五座城市，在城市场景中发现当地节气美食，完成“品鉴”后获得城市印章，集齐五城后展开完整终章长卷。

核心循环：

```text
进入绘卷 → 沿运河选城 → 进入城市场景 → 发现美食
→ 展开文化与季节信息 → 完成品鉴 → 获得印章
→ 返回运河继续旅行 → 集齐五城 → 展开终章长卷
```

### 1.3 成功标准排序

投入优先级必须遵循：

1. **完整体验是否成立**：有开场、探索、反馈、进度与终章；
2. **视觉资产是否精细**：食物像插画，不像基础几何练习；
3. **Renderer 是否可靠**：坐标、层级、变换、颜色、渐变可预测；
4. **交互是否清楚**：键鼠一致、可逆、即时反馈、不会卡死；
5. **架构是否适量**：足够支撑作品，但不为抽象而抽象。

视觉资产数据质量高于框架复杂度。若预算有限，应减少抽象层，把时间投入食物轮廓、材质、光影、纹理与场景构图。

## 2. 范围约束：保留什么，暂不做什么

### 2.1 必须保留的核心能力

- Primitive：丰富但边界明确的基础绘图单元；
- Style：RGB256、描边、填充、线宽、文字样式；
- Transform：平移、缩放、旋转、枢轴；
- Group：组合与嵌套；
- Path：复合路径命令；
- Gradient：按能力矩阵分阶段实现并验证；
- Layer / Z-order：稳定、可预测的绘制顺序；
- Parser / Renderer：声明式绘图数据到 Turtle 的唯一渲染通道；
- AppState：清晰的小型状态机；
- 输入、命中测试、轻量动画和静态/动态分层绘制。

### 2.2 当前禁止或降级的内容

- 不创建 EventBus，除非已经出现无法用 App 直接调用解决的实际耦合；
- 不实现 React-like 状态框架；
- 不实现复杂 CSS-like 选择器、继承、级联系统；
- 不实现复杂动画编排 DSL；
- 不承诺真正 alpha compositing；
- 不追求 60 FPS；目标是静态画质优先，交互动画体感平滑，通常 15–30 FPS 可接受；
- 不声称自定义双缓冲；只能表述为关闭 Turtle 自动刷新、批量绘制后统一 `screen.update()`；
- 不构建复杂通用 UI 控件库；本项目界面是一幅画，不是后台管理系统；
- 不加入背景音乐、联网、外部图片依赖、数据库等非核心能力，除非用户另行要求。

### 2.3 代码规模原则

行数不是 KPI。合理预估仅用于控制投入：

| 部分 | 建议量级 |
|---|---:|
| Renderer、Parser、几何与样式 | 600–1000 行 |
| App、状态、输入、场景、动画 | 400–700 行 |
| UI/场景绘图数据 | 500–1000 行 |
| 五城十味视觉资产数据 | 1500–3000 行 |

真正值得投入的部分应主要是视觉与内容，而不是 EventBus、CSS 仿制或框架层。

## 4. 声明式矢量 DSL 规范

### 4.1 总体原则

每个物品对象持有 `drawing_data`。`drawing_data` 是按绘制顺序排列的列表；每项第 0 位是类型码，后续参数遵循该类型的固定 schema。内容数据不得直接调用 Turtle。

建议统一形式：

```python
[TYPE_CODE, geometry, style_or_options]
```

其中：

- 坐标默认使用局部归一化坐标 `[0.0, 1.0]`；
- `bounds = (left, bottom, width, height)`；
- `x_abs = left + x * width`；
- `y_abs = bottom + y * height`；
- 长度默认相对 `min(width, height)`，避免非等比 bounds 把圆拉坏；
- 列表顺序即默认 z-order；如存在显式 `z`，Parser 应稳定排序，同 z 保持原顺序；
- 所有数据先校验再渲染；错误信息必须包含 item 索引、类型码和参数问题。

### 4.2 核心类型码（共 14 种）

不要再写“15 种”而只列出 12 种。以下清单是本规格的明确基线：

| 码 | 名称 | geometry 示例 | 主要用途 |
|---|---|---|---|
| `P` | Point | `[x, y, size]` | 点状纹理、芝麻、糖粒 |
| `L` | Line/Polyline | `[[x,y], ...]` | 叶脉、轮廓线、装饰线 |
| `R` | Rectangle | `[x, y, w, h]` | 面板、色带、背景 |
| `RR` | RoundedRect | `[x, y, w, h, radius]` | 题签、提示牌 |
| `C` | Circle | `[cx, cy, r]` | 食材、盘子、印章 |
| `E` | Ellipse | `[cx, cy, rx, ry]` | 阴影、盘沿、食物体积 |
| `G` | Polygon | `[[x,y], ...]` | 任意封闭轮廓 |
| `A` | Arc | `[cx,cy,r,start,end]` | 蒸汽、水波、盘纹 |
| `Q` | Quadratic Bézier | `[[p0],[p1],[p2]]` | 柔和曲线 |
| `B` | Cubic Bézier | `[[p0],[p1],[p2],[p3]]` | 船路、绳结、复杂轮廓 |
| `PATH` | Compound Path | `[["M",...],["L",...],["Q",...],["C",...],["Z"]]` | 精细轮廓与连续曲线 |
| `RG` | Ring | `[cx,cy,r_inner,r_outer]` | 盘沿、月饼边、节气轮 |
| `T` | Text | `[x,y,text]` | 标题、题跋、说明 |
| `GR` | Group | `[children]` | 复用、嵌套与整体变换 |

不要为了“丰富”继续增加可以用组合表达的类型。胶囊、扇形、花瓣、印章等应优先由上述 primitive 组合，只有多个正式资产反复需要且组合明显笨重时才新增类型。

### 4.4 Transform 结构与顺序

```python

    "translate": [dx, dy],
```

## 5. 颜色、透明度与渐变的真实能力

### 5.1 RGB256

外部数据统一使用 `(r, g, b)`，每个通道必须是 `0–255` 的整数。进入 Turtle 前统一转换为 Tk/Turtle 可接受的颜色格式。颜色函数必须测试：边界值、非法长度、浮点数、负数、超过 255、字符串等。

### 5.2 RGBA/透明度策略

标准 Turtle/Tk Canvas 不提供通用的原生 alpha compositing。因此：

- 可以接受 `(r, g, b, a)` 作为输入便利格式，但必须在绘制前预混成纯 RGB；
- 混色公式：`out = alpha * foreground + (1 - alpha) * background`；
- `a` 可统一为 `0–255`，内部转为 `0.0–1.0`；
- 当背景不明确时，不允许默默假装透明；应要求 `blend_with` 或使用场景已知底色；
- 阴影、高光、薄雾等优先用预混色和多层形状模拟；
- 文档只能写“透明感模拟”或“RGBA 输入预混”，不能写“支持真正 RGBA 透明绘制”。

### 5.3 渐变数据格式

```python
{
    "type": "linear",
    "stops": [
        [(255, 80, 50), 0.0],
        [(255, 210, 80), 0.55],
        [(120, 58, 32), 1.0],
    ],
    "angle": 45,
    "steps": 36,
}
```

径向渐变：

```python
{
    "type": "radial",
    "stops": [[(255, 228, 138), 0.0], [(153, 81, 34), 1.0]],
    "center": [0.42, 0.38],
    "steps": 32,
}
```

色标位置必须单调递增，范围为 `[0,1]`，至少两个 stop；允许 2、3、5 个色标。颜色插值要覆盖跨多段 stop 的情况。

### 5.4 渐变实现路线

不要用一个渐变矩形覆盖任意多边形。线性渐变需要真实裁切：

1. 将目标轮廓表示为 polygon；圆/椭圆可在需要时采样为足够平滑的 polygon；
2. 根据角度得到渐变轴，将顶点投影到轴上；
3. 沿投影范围切分为 N 个平行色带；
4. 使用半平面裁切/Sutherland–Hodgman 将每条色带裁到目标 polygon 内；
5. 按色带中心位置从多色标中插值得到颜色；
6. 最后单独绘制一次完整轮廓描边，避免色带边缘破坏轮廓。

径向渐变优先通过从外向内的同心圆/椭圆/近似轮廓实现。任意多边形的径向渐变不是 G1 必须项；具体资产可用多层局部高光替代。

## 6. Renderer 验证体系（G1）

### 6.1 先做代码审计

审计输出至少回答：

- 当前实际存在多少种类型码，定义、Parser 和 Engine 是否一一对应；
- 哪些方法只是占位，哪些真正调用了 Turtle；
- 坐标、半径、线宽、字体大小各自如何随 bounds 缩放；
- Group 变换是否真的传递到所有子项；
- 渐变是否裁切到轮廓；
- RGBA 是否真正混色，还是仅丢弃 alpha；
- 圆角矩形、椭圆、环、二次/三次贝塞尔是否绘制正确；
- 当前导入为何依赖 `sys.path` 修改；
- 示例是否真正启动并渲染，而不只是 import 成功；
- 是否存在未提交/与本任务无关的改动。

### 6.2 自动测试

纯计算必须脱离 GUI 测试：

- RGB/RGBA 校验与预混色；
- 多色标插值；
- 归一化坐标到绝对坐标；
- 变换矩阵与嵌套顺序；
- Bézier 起点、终点、中间采样；
- polygon 裁切；
- DSL schema 校验和清晰错误信息；
- z-order 稳定排序；
- AppState 合法/非法转换；
- 鼠标命中边界。

### 6.3 三套可视化 Gallery

#### A. `primitive_gallery.py`

一屏展示全部 14 种 primitive。每一格包含名称和至少一个代表性样例。重点检查：位置、尺寸、填充、描边、圆角、闭合、曲线连续性、文字对齐、层级。

#### B. `gradient_gallery.py`

必须覆盖：

- 2、3、5 stops；
- 0°、30°、45°、90°、135°；
- rectangle、rounded rectangle、circle、ellipse、polygon；
- radial circle、radial ellipse、ring；
- 色标边界与无效输入；
- 渐变不得越出轮廓。

#### C. `transform_gallery.py`

必须覆盖：

- translate、uniform scale、non-uniform scale、rotate；
- 非中心 pivot；
- group；
- nested group；
- 父子组合变换；
- transform 后的描边与 z-order。

### 6.4 可视化证据

每个 Gallery：

- 可单独运行；
- 有固定窗口尺寸和浅色背景；
- 画面内标注示例名；
- 将运行命令、测试日期、平台、已知限制记入 `docs/visual-qa.md`；
- 能自动导出画布时保存为 PostScript/PDF/PNG；环境不支持时明确要求人工截图，不要声称已经视觉通过。

### 6.5 G1 验收条件

- `python -m pytest` 全部通过；
- 三个 Gallery 均实际启动，用户/执行环境可见；
- 14 种类型定义、解析、绘制三方一致；
- import 不再靠各模块修改 `sys.path`；
- 功能矩阵已按实测标记；
- 已知限制写清楚；
- 没有开始批量绘制五城十味。

## 7. 体验与状态设计（G2）

### 7.1 唯一状态源

```python
class Mode(Enum):
    INTRO = auto()
    MAP = auto()
    CITY = auto()
    FOOD_DETAIL = auto()
    FINALE = auto()

@dataclass
class AppState:
    mode: Mode
    current_city: int
    current_food: int
    visited_cities: set[str]
    discovered_foods: set[str]
    stamped_cities: set[str]
    current_season: str
    help_open: bool = False
    transition_locked: bool = False
```

`App` 直接调用 `next_city()`、`previous_city()`、`enter_city()`、`open_food()`、`complete_tasting()`、`back()`、`toggle_help()`。不使用 EventBus。

### 7.2 合法状态流

```text
INTRO --Enter/Click--> MAP
MAP --选择城市--> CITY
CITY --选择美食--> FOOD_DETAIL
FOOD_DETAIL --完成品鉴--> CITY
CITY --Esc/Back--> MAP
MAP --五城印章完成--> FINALE
FINALE --Enter--> MAP（保留收集进度）
```

帮助层是 overlay，不替换主 mode；打开时阻止底层输入，关闭后回到原画面。动画期间使用 `transition_locked` 防止重复触发；`Esc` 应尽量安全返回，任何状态都不应把用户困住。

### 7.3 画布与层

基准画布：`1200 × 800`，安全边距 40。若窗口尺寸变化，整体按设计坐标等比缩放并居中，避免非等比拉伸。

建议使用少量独立 Turtle 作为逻辑层：

| 层 | 内容 | 更新策略 |
|---|---|---|
| background | 宣纸、城市背景、河道 | 场景切换时重绘 |
| content | 食物、建筑、题签 | 选择变化时重绘 |
| dynamic | 船、水波、蒸汽、落花 | 动画帧局部清除重绘 |
| overlay | 帮助、详情、印章反馈 | 打开/关闭时重绘 |

不要每一帧清空并重画整个高精度静态场景。

### 7.4 全局输入

| 输入 | MAP | CITY | FOOD_DETAIL | FINALE/其他 |
|---|---|---|---|---|
| `W/↑` | 北上一个城市 | 可选上一个热点 | 滚动/无操作 | 无操作 |
| `S/↓` | 南下一个城市 | 可选下一个热点 | 滚动/无操作 | 无操作 |
| `A/←` | 上一个城市 | 上一道美食 | 上一信息页 | 无操作 |
| `D/→` | 下一个城市 | 下一道美食 | 下一信息页 | 无操作 |
| `Enter` | 进入当前城市 | 打开当前美食 | 完成品鉴/关闭详情 | 开始/重新游览 |
| `Space` | 船/城市轻互动 | 当前场景互动 | 完成品鉴 | 终章轻互动 |
| `Esc` | 返回开场可选 | 返回地图 | 返回城市 | 关闭覆盖层 |
| `H` | 打开/关闭帮助 | 同左 | 同左 | 同左 |
| 鼠标点击 | 选择城市 | 选择美食/返回 | 品鉴/关闭 | 主要动作 |

键盘与鼠标必须到达相同核心功能。可点击区必须明显大于细线图形本身，并提供选中反馈。不要使用 Emoji 作为正式界面图标；船、印章、返回符号等用 Turtle 矢量图形或文字实现。

## 8. 逐屏 UI/UX 规格

### 8.1 INTRO：卷轴开场

画面：暖白宣纸背景，左右卷轴边缘，中央标题“运河四季·食味行舟”，副题“一河通南北，五味见四时”。下方仅一个明确提示：“按 Enter 或点击启程”。

动画：0.8–1.2 秒卷轴展开或墨迹显现；可跳过。标题稳定后停止持续动画，避免喧闹。

验收：首次用户 3 秒内知道如何开始；Enter 和点击均有效；动画中重复输入不会创建多个计时器。

### 8.2 MAP：交互式运河长卷

画面：

- 宣纸底；
- 一条自北向南的曲线运河；
- 五座城市用风格统一、主题不同的码头/印章节点表示；
- 小船停在当前城市；
- 已访问城市为实色并盖章，未访问城市为淡墨；
- 右上角显示“运河食鉴 2/5”等轻量进度；
- 一枚小型四季轮指向当前城市/食物对应季节。

交互：上下/W/S 沿河选择，点击城市直接选择。切换城市时，小船沿预定义 Cubic Bézier 路径移动约 0.6–0.9 秒；城市名淡入；河面产生 1–2 圈水波。若用户开启减少动画配置，直接切换并保留短反馈。

验收：地图不是五个矩形按钮；当前位置、已完成状态、下一步动作一眼可辨。

### 8.3 CITY：城市微型场景

画面不使用传统“左图右文卡片”。每城是一幅微型画，两个食物作为场景中的可发现焦点；底部以简洁题签提示左右切换与 Enter 查看。

进入时：背景先出现，城市题字随后淡入，食物最后分层绘制。返回地图必须始终可用。

### 8.4 FOOD_DETAIL：三层揭示

详情体验分为三层，不要一进入就堆满文字：

1. **视觉层**：食物作为主角，展示体积、纹理、盘饰、蒸汽/落花等；
2. **发现层**：标题以题跋形式出现，如“扬州·蟹粉狮子头”，落一枚小型城市印记；
3. **品鉴层**：再次 Enter/点击后展开节气、主要食材、简短“运河记忆”文案，并记录发现。

完成首次品鉴后出现一次 0.4–0.7 秒的印章落下反馈；重复查看不重复刷印章，但可以重播轻量视觉反馈。

详情文字每块控制在 2–4 行，字号和对比度足够。历史与文化文案若无可靠来源，写成克制的描述性文字，不编造具体年代、人物或典故。

### 8.5 HELP：帮助覆盖层

半透明感通过与当前背景预混后的纯色遮罩模拟。列出 7 个以内的主要按键。H、Esc 或点击关闭。打开时暂停非必要动画，关闭后恢复。

### 8.6 FINALE：完整终章

触发条件：五座城市均获得城市印章。画面拉远/重构为一幅完整运河长卷，五城沿河出现，五枚印章依次落位，标题“运河四季·人间五味”与句子“一河通南北，五味见四时”出现。

用户按 Enter 可返回地图自由游览；收集状态保留。本项目必须有明确终章，不能只是无限左右切换。

| 城市 | 视觉主题 | 美食 1 | 美食 2 | 主季节/氛围 | 城市特效 |
|---|---|---|---|---|---|

| 天津 | 码头、海河波纹、桥影、蓝金 | 狗不理包子 | 十八街麻花 | 春 / 冬 | 水波、桥灯倒影 |
| 扬州 | 园林、柳枝、拱桥、烟雨青绿 | 蟹粉狮子头 | 蟹黄汤包 | 秋 / 春 | 柳叶轻摆、细雨纹 |

### 9.1 每道美食的数据合同

```python
@dataclass(frozen=True)
class FoodSpec:
    id: str
    city_id: str
    name: str
    season: str
    subtitle: str
    ingredients: tuple[str, ...]
    story: str
    drawing_data: list
    interaction: str | None
    bounds: tuple[float, float, float, float]
```

每道正式美食必须至少包含：

- 可识别的非基础几何轮廓；
- 主光、副光、暗部、接触阴影；
- 描边层级与局部颜色变化；
- 至少一种材质纹理；
- 盘子/器皿或合理承托关系；
- 2–4 个辨识度细节；
- 与冷热/季节相符的一种轻量动态或互动；
- 题签与简短文化内容。

单个精细食物允许使用 30–100 个 primitive，必要时更多。优先复用纹理生成器和小组件，但不得让十道菜都像同一个模板换色。

### 9.2 内容资产分解建议

- 烤鸭：完整鸭身轮廓、焦糖色皮层渐变、切片暗线、盘沿、黄瓜/葱丝点缀；
- 月饼：圆角/花边外轮廓、压花纹样、烘烤色差、切面或碎屑；
- 包子：褶皱曲线、蒸笼、接触阴影、蒸汽；
- 麻花：多股交织路径、油炸高光、糖粒/芝麻点；
- 狮子头：不规则肉丸轮廓、颗粒纹理、汤汁高光、青菜承托；
- 汤包：薄皮褶皱、半透感预混色、蒸笼、醋碟；
- 桂花糕：分层截面、米糕颗粒、桂花点、瓷盘；
- 松鼠桂鱼：鱼身曲线、菱形刀花、酱汁高光、尾鳍与松仁；
- 龙井茶：茶盏/壶、茶叶曲线、茶汤渐变、茶汽；
- 西湖醋鱼：鱼身、鳞片暗纹、酱汁、姜丝/葱丝与盘中倒影。

## 10. 动画与性能

### 10.1 动画必须表达信息

| 动画 | 表达的信息 |
|---|---|
| 船沿河移动 | 城市切换 |
| 水波扩散 | 当前城市激活 |
| 卷轴展开 | 作品开始/页面进入 |
| 食物分层出现 | 从场景进入视觉聚焦 |
| 印章落下 | 完成发现与收集 |
| 季节轮转动 | 当前食物所属季节变化 |
| 蒸汽 | 热食 |
| 桂花/柳叶/荷叶 | 城市与季节身份 |
| 墨迹过渡 | 场景切换 |

禁止所有按钮持续呼吸、所有物体旋转、全屏永久粒子等无信息动画。

### 10.2 调度策略

- 使用 `time.perf_counter()` 计算真实 elapsed/delta，不把 `ontimer(16)` 当成 60 FPS 证明；
- 默认目标帧间隔可设 33–50 ms；复杂环境允许降帧；
- 动画插值基于时间而非帧数，掉帧时仍按正确进度结束；
- 每个动画结束后取消/停止对应 tick；切场景不得残留旧计时器；
- 连续输入去抖，动画锁期间忽略或只保留最后一个导航意图；
- 动态层单独清除，重用预计算的路径采样和静态几何；
- 提供 `reduced_motion` 配置以快速跳过长过渡；
- 不使用 `time.sleep()` 阻塞 GUI 主线程。

### 10.3 性能验收

在目标电脑上记录：

- 启动到开场可交互的时间；
- 地图切城动画平均帧耗时/体感；
- 高精度食物首次绘制耗时；
- 连续快速按键是否卡死或积压；
- 切换 20 次场景后是否出现越来越慢或重复计时器；
- 静态画面是否闪烁。

目标不是一个虚假的 FPS 数字，而是：输入有即时反馈、过渡不阻塞、静态画质稳定、长时间操作不劣化。

## 11. 高精度粽子验收样例（G3）

尽管粽子不一定属于最终五城十味，它作为 Renderer 的统一“压力样例”保留。完成体验闭环后，只制作这一只，不要同时做月饼和茶壶。

### 11.1 必须包含

- 不是一个简单三角形，而是由 Bézier/PATH 形成的自然立体轮廓；
- 至少 3 个叶片分区，边缘相互压叠；
- 主叶脉和若干次级叶脉，线宽/颜色有层级；
- 绳带环绕关系与绳结，前后遮挡正确；
- 主光、暗部、边缘高光与接触阴影；
- 至少 3 组局部绿色，避免纯色平面；
- 盘子或宣纸承托关系；
- 少量蒸汽/粽叶装饰，但不喧宾夺主；
- 缩放到 70%、100%、130% 时仍保持轮廓稳定；
- 在不同 bounds 位置渲染时不越界、不变形。

### 11.2 视觉判断

第一眼应明显是“插画化粽子”，而不是“几个几何形状拼起来的粽子”。至少从以下维度人工评分，每项 1–5 分，平均不低于 4，且没有低于 3 的项：

| 维度 | 判断问题 |
|---|---|
| 轮廓 | 外形自然、可识别、有体积吗？ |
| 材质 | 能看出粽叶、绳、阴影的区别吗？ |
| 光影 | 主光与暗部是否统一，不像随机色块？ |
| 细节 | 叶脉、压叠、绳结是否可信？ |
| 构图 | 主体、盘子、题签与留白是否平衡？ |
| 风格 | 是否与宣纸、中国传统色和后续城市风格兼容？ |

### 11.3 G3 通过条件

- `examples/zongzi_showcase.py` 可独立运行；
- 自动测试仍全部通过；
- 人工视觉评分通过；
- 证明至少实际使用了 PATH、Group/Transform、Layer、Style、预混阴影和一种已验证渐变；
- 将制作中遇到的 DSL/Renderer 缺口先补回核心，再开始十道正式资产。
